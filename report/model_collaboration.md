# 工程决策、验证与大模型协作

本作品的技术主体是一套贯通 RISC-V 指令执行、二维图形加速、DDR 显示、USB 输入及 I²S 音频的可运行 SoC。工程难点集中于有限片上存储下的整帧一致性、CPU 与存储系统的性能配合，以及 PS/PL 在应用切换时的资源生命周期。

以下案例依据随包源码、测试数据和开发记录整理，是工程回顾。对应的专题整理、原始提示词和模型回答节选见 [技术协作记录](collaboration/README.md)。

## 1. 协作分工与工程方法

参赛者提出作品目标、硬件条件和交互要求，提供现场操作反馈，确认展示效果与最终采用版本。大模型参与源码分析、RTL/C/Python 实现、测试脚本编写、调试与文档整理。工程自主贡献、第三方复用和 AI 参与分别记录，来源见 [贡献与来源](contribution_and_sources.md)。

开发流程以可检验的问题为起点：先明确接口和约束，再提出实现候选；用仿真及负例检查机制，用板端输出检查系统表现，最后固定程序、硬件与数据的对应关系。验收依据包括源码、原始计数、CRC、像素参考和重建结果，而非模型回答中的判断。

| 技术问题 | 关键设计判断 | 可核对的结果 |
| --- | --- | --- |
| CPU 热命中仍耗费多个周期 | 联合分析执行阶段、分支及数据响应，避免只扩大缓存 | 105 MHz；CoreMark 371.852；CPU 核心 6387 LUT |
| 480000 字节画面超过暂存区容量 | 分带绘制与整帧提交分开管理 | 256 KiB 暂存区复用，完成 800×600 全像素提交 |
| 应用退出可能卡住 ARM MMIO | 按实际依赖顺序完成或取消帧，再停止生产者 | 旧 HOLD 死锁复现、空闲及在途 DMA 安全取消用例 |
| 平均 FPS 难以证明显示连续性 | 同时检查完成帧、扫描和遗漏计数 | TILE 512、位图 96、Alpha 32 对象的连续不少于 60 秒记录 |
| 当前源码可能不能重建已测程序 | 每个程序分别冻结源码、命令、素材与预期哈希 | 八个 RV32 程序从独立目录重建，产物逐字节一致 |

## 2. CPU：从周期消耗定位到执行与存储协同

早期记录发现，缓存热命中并没有消除处理器的主要等待：当时 ALU 指令仍经过六拍、分支经过五拍，DDR Load 的请求发起和返回交接也有额外等待；指令与数据共用直接映射缓存，还会出现同索引冲突。因此，单纯扩大容量不能同时解决执行阶段等待和映射冲突。

最终实现把优化落实到相互配合的机制：五个主流水阶段、预测与旁路、受条件限制的相邻双指令 ALU 路径，以及 64 KiB 四路缓存和指令缓冲。接口上的重点是响应归属、控制流变化和依赖条件，确保性能路径服从正确的指令与数据关系。

性能统计使用板端实际时钟、运行周期与 CoreMark 校验值。105 MHz 下得到 371.852 CoreMark，即约 3.541 CoreMark/MHz；效率分母采用 CPU 核心的 6387 LUT，得到约 0.05822 CoreMark/LUT。整套 SoC 的 23447 LUT 单列，避免将不同范围的资源数据混为一谈。早期周期观察用于解释瓶颈，不直接换算为最终 CoreMark 的提升倍数。

核对入口：[顶层配置](../hardware/inputs/rtl/top_system640.v)、[CPU 流水实现](../hardware/inputs/rtl/rv32i_pipeline_core.v)、[指标复算](../verification/recheck_metrics.py)、[早期对话节选](collaboration/earlier_cpu_and_verification.md)。

## 3. 图形：把容量限制转化为明确的帧事务

800×600 RGB332 画面需要 480000 字节，单个 256 KiB 暂存区只有 262144 字节。工程采用两个 800×300 分带，每带 240000 字节，复用同一暂存区，再向 DDR 后台帧缓冲搬运。

这一方案的难点不仅是拆分坐标，还包括帧的可见时机。`native_frame_commit` 按上带、下带顺序接收搬运，两个分带都完成后进入 `READY`，到显示帧边界才切换前台缓冲并增加完整帧计数。分带搬运次数不会被计为完整画面数量；错误、取消及在途总线事务通过单独的排空路径处理。

验证覆盖理想响应、总线背压、软件像素提交、未初始化数据拒绝和并发 PCM。全像素用例明确检查 480000 个像素，既检查可见画面，也检查末尾像素与控制顺序。这使存储复用、提交协议和显示正确性具有共同的验证依据。

核对入口：[分带软件接口](../software/source/stable/software/native800_frame.c)、[整帧提交状态机](../hardware/inputs/rtl/native_frame_commit_20261031.v)、[仿真用例清单](../sim/fixtures.json)、[仿真结果](../verification/reproduction.json)。

## 4. PS/PL：从 HOLD 死锁分析提炼生命周期规则

一次应用退出问题暴露了跨处理器与硬件状态机的循环依赖：HOLD 停止生产者，停止操作的响应又等待帧引擎空闲，而未完成帧仍需要生产者提交剩余分带。此时 Python 侧增加超时不能解除 ARM 已经进入的 MMIO 等待。

修正后的顺序由依赖关系决定：正常退出先让生产者完成最后一帧；异常退出走经过验证的取消与总线排空路径。确认在途访问结束后，再进入停止状态并释放程序、显示缓冲等资源。不能仅凭发送过停止请求或进程消失就判断 DMA 已经安全结束。

测试台保留旧顺序的死锁复现，并分别覆盖 `dma_busy=0` 和 `dma_busy=1` 的安全取消路径。由此得到的经验进一步整理为可复用的 PYNQ 生命周期工作流：先画清生产者、消费者和完成条件，再设计退出协议，并同时验证错误顺序和正确顺序。

核对入口：[HOLD 测试台](../sim/cases/hold_retirement/tb.sv)、[板端退出检查](../runtime/package/native_session.py)、[通用生命周期方法](../skill/owner_lifecycle.md)。

## 5. 测量：区分平均速度、连续显示与版本身份

平均帧率接近 60 并不足以证明每次扫描都拿到新帧。本工程同时核对计时周期、完整帧数、扫描数与遗漏计数，对 TILE、位图、Alpha 的默认负载使用不少于 60 秒的连续窗口。星际弹幕的连续窗口与鸡蛋兄弟的场景计量段分别说明，不把不同时间窗口当作同一种测试。

协作中还发现，旧 Alpha 测量对应的程序字节与当前版本不同。处理方式是按程序、bit、HWH 的 SHA256 重新匹配证据，并从原始计数复算指标。历史数据的日期或目录名不能替代版本对应关系。

另一个纠错点来自软件绘制：低帧率会拉长完整遥测包的接收时间，应分别判断“持续有进展的慢包”和“完全无进展的超时”。修正需同时覆盖完整慢包、停滞和坏包，保留 CRC 与安全退出检查。

核对入口：[CPU/图形原始数据](../verification/data)、[图形指标检查器](../verification/recheck_metrics.py)、[两游戏与 PCM 复核](../verification/recheck_final_visual.py)、[相关协作记录](collaboration/current_ui_and_delivery.md)。

## 6. 复现：让交付源码能够解释每一个程序映像

八个程序来自不同阶段，使用的 UI、素材和条件编译路径也不同。复现包采用逐目标构建配方，记录源码、编译命令、素材依赖和预期二进制哈希；编译器依赖检查保证头文件来自包内，菜单汇编引用的二进制素材也随包冻结。

第一次命令提取曾把 `gcc --version` 误认作编译步骤。修正后，程序在独立目录中重新编译、链接并转换为二进制，八个结果均与随包映像逐字节一致。硬件则从 RTL、IP、约束与初始化数据重新综合、布局布线和导出，不以旧工程缓存替代源码构建。

验证器本身也需要检查：该版本 XSim 在预期 `$fatal` 后仍可能返回 0，因此负例必须命中指定断言，并拒绝其他错误或正例标记。这样既验证设计，也检查自动化流程是否会把失败误报为成功。

核对入口：[软件重建脚本](../software/rebuild.py)、[构建配方](../software/recipes.json)、[硬件重建脚本](../hardware/rebuild.py)、[仿真重放](../sim/replay.py)、[复现收据](../verification/reproduction.json)。

## 7. 从本作品提炼可迁移的 Skill

技能包把上述经验分为可直接执行的产物检查器，以及需要结合目标接口使用的生命周期工作流：

| 来源问题 | 提炼的方法 | 验证及迁移方式 |
| --- | --- | --- |
| 同名文件、旧记录与新程序不一致 | 构建身份与文件 SHA256 绑定 | 更换产物目录和清单即可用于其他项目 |
| 空比较、错误范围可能产生假通过 | 非空、等长或明确边界的二进制比较 | 8 项自检覆盖正确与错误哈希、错误字节、空范围、越界、目录逃逸、空清单及合法切片 |
| 板端异常退出时缓冲仍被硬件访问 | 依据生产者/消费者依赖确定完成、取消、排空和释放顺序 | 本工程用死锁与安全取消用例验证；迁移时替换为目标设计的接口协议 |

检查器只使用 Python 标准库，不绑定本作品寄存器、SSH 账户或固定地址。另一支队伍可以直接运行离线检查；板端生命周期方法则要求结合其实际 RTL 与驱动。技能的适用范围、命令及失效条件见 [skill/README.md](../skill/README.md)。
