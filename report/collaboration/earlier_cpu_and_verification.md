# 处理器瓶颈分析与分阶段验证

本记录归纳早期处理器优化与硬件验证中的技术问题、分析依据和验收方法。原始提示词、模型回答节选及来源位置见 [对应 JSON](earlier_cpu_and_verification.json)，按 E1—E4 编号关联。

## 1. 优化目标与问题分解

该阶段将优化目标限定为多周期执行开销与缓存冲突，先定位等待来源，再确定修改范围（E1）。

分析将性能问题分为执行阶段等待、存储请求交接和缓存映射冲突三个层面。这样能够区分增加缓存容量可以改善的问题，以及必须通过流水与接口调整处理的问题。

## 2. 周期消耗与缓存冲突

模型根据当时的源码和开发记录提出以下观察（E2、E3）：

| 观察 | 技术含义 | 对照分析方法 |
| --- | --- | --- |
| 热分支循环 CPI 仍约为 5.73 | 提前取指的收益尚未消除整个执行流程的等待 | 分别统计取指、执行、访存和控制转移阶段的周期 |
| 热命中下 ALU 指令经过六拍，分支经过五拍 | 缓存命中与低执行周期并不等价 | 使用紧凑循环减少工作集变化，观察阶段开销 |
| Load 到 MEMORY_WAIT 阶段才发出请求，命中仍有交接等待 | 请求发起和返回交接影响有效执行效率 | 沿实际请求与响应链路检查等待条件 |
| 指令和数据共用直接映射缓存，可能发生同索引冲突 | 容量扩大不能替代对映射冲突的分析 | 改变地址对齐与重复工作集，区分容量和冲突影响 |

这些数值描述当时的开发阶段，用于说明瓶颈定位过程；最终五主级流水、四路缓存配置及性能结果由当前工程源码与报告给出。

## 3. 将分析转化为可验证的优化

该阶段提出用重复执行、地址对齐和紧凑循环构造对照负载，分别分析执行和存储开销。局部机制的收益需要在完整指令流中复核，并同时检查相关依赖、控制转移和存储响应，避免仅凭单一路径变快就判断处理器整体改善。

最终实现及测量的核对入口包括：

- [CPU 流水实现](../../hardware/inputs/rtl/rv32i_pipeline_core.v)：执行、旁路、相邻指令配对与提交关系。
- [缓存实现](../../hardware/inputs/rtl/ddr_read_cache.v)：标签比较、完整行填充和请求交接。
- [指标复算工具](../../verification/recheck_metrics.py)：从原始周期、CRC 与资源报告复算结果。

## 4. 仿真 综合与实现分别验收

DDR 位图阶段曾出现“代码、仿真和综合已通过，而布局布线重试未通过”的结果（E4）。该记录说明功能验证与物理实现承担不同的验收任务：前者检查逻辑行为，后者检查目标器件上的实现可行性和时序条件。

工程因此分别记录源码、仿真、综合、布局布线及板端结果。最终完整构建与导出结果见 [复现记录](../../verification/reproduction.json)，不以某一个中间阶段的通过替代完整实现结论。
