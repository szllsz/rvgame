# 图形交互验证与工程复现

本记录按技术主题整理界面优化、性能测量、协议纠错和源码复现过程。原始提示词与模型回答节选见 [对应 JSON](current_ui_and_delivery.json)，按 R1—R7 编号关联。文中的阶段测量说明当时的验证过程，最终提交指标见设计报告及验证目录。

## 1. 界面信息与功能验证保持一致

需求同时覆盖交互优化、结果核查和工程复现，要求以实际测量和来源记录支撑结论（R1）。

界面检查发现，未使用的分数字段固定显示为零、缩略图放大后失真，暂停页与主场景的层级不一致。优化围绕真实可用的信息重新组织首页、侧栏和暂停面板，保留弹幕绘图区与应用逻辑，显示实际弹量、擦弹及测量结果（R2）。

验证先检查软件编译和像素输出，再进入板端测试。该阶段完成了 RV32 编译及 18 组全画面像素比对（R3）。界面改动与性能测试分别检查，防止布局调整掩盖功能变化或负载变化。

## 2. 源码依赖与二进制逐项对应

多个程序来自不同开发阶段，公共 UI、素材和条件编译路径并不完全相同。复现包因此按程序分别冻结源码、构建命令和预期产物，保留已测程序的字节身份。

一次自动提取错误将 `gcc --version` 当作编译命令（R4）。修正后的验证不以命令运行成功为终点，而是检查实际编译依赖、生成产物及预期哈希。该阶段八个程序在含空格的独立目录中重建，二进制逐字节一致，编译依赖未引用原工作树（R5）。

对应方法体现为三项可执行检查：

1. 构建命令与具体程序、源文件及素材对应。
2. 构建依赖全部落在交付包中，避免依赖开发者机器上的隐含文件。
3. 重建产物与测量时的程序映像逐字节比较，保证源码能够解释所提交的结果。

核对入口：[软件构建配方](../../software/recipes.json)、[独立重建脚本](../../software/rebuild.py)、[复现记录](../../verification/reproduction.json)。

## 3. 连续显示测量与遥测故障分开分析

一次默认负载测量记录了连续 60.70 秒、3642 帧对应 3642 次扫描，漏扫描与漏逻辑 tick 均为零；随后切换至更高负载的软件绘制时出现遥测超时，控制器完成安全释放并恢复稳定版本（R6）。

这两项结果分别说明显示性能和协议行为。默认场景的测量通过不能覆盖所有绘制模式；较慢的完整数据包也不能直接判为运行停滞。纠错过程中分别检查慢速完整包、无进展超时和坏包，使接收条件能够区分持续进展与异常停滞。

相关本机检查通过记录见 R7。完整帧、PCM CRC、程序身份和退出结果的复核入口为 [两游戏测量检查器](../../verification/recheck_final_visual.py)。

## 4. 测量结果必须匹配程序版本

资料核对发现，旧 Alpha 测量记录中的程序字节与所分析版本不同。处理方式是依据程序、bit、HWH 的文件身份选择对应测量，再修正报告中的引用关系（R7）。

这一过程把版本管理纳入性能验证：同名程序或较新的目录名都不足以证明结果可复用，必须确认测试对象一致，再从原始计数复算指标。方法被进一步提炼为 [产物与黄金参考校验技能](../../skill/README.md)，用于其他工程的离线结果核对。
